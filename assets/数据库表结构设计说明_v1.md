## 二、设计核心原则

### 2.1 三端物理隔离
所有权限/组织/日志相关表 **物理拆分为 saas→pmc / tmc / mmc 三套**，禁止跨端共用一张表（避免锁竞争 + 数据安全隔离 + 独立迭代）。

### 2.2 单表共享的例外
以下 3 类表 **跨端单表共享**，通过 `platform` 字段区分：

| 表 | 共享理由 |
|---|---|
| `rules` (Casbin) | Casbin 引擎设计如此，通过 `dom` 字段隔离三端 |
| `data_permission_policy` | 策略类型一致，通过 `platform` + `tenant_id` 隔离 |
| `user_third_party_auth` / `user_third_party_login_log` | 三端数据结构完全一致，支持同一微信 unionid 同时绑多端账号 |

### 2.3 唯一约束差异化

| 类型 | 范围 | 例 |
|---|---|---|
| PMC 端 user | 全局唯一 | `username` 全平台唯一 |
| TMC/MMC 端 user | 租户内唯一 | `(tenant_id, username)` 复合唯一 |

### 2.4 脱敏字段三件套
每张 `*_user` 表的 phone/email 都有 **明文(脱敏) + 密文 + 哈希** 三个字段，唯一约束切到哈希字段。

### 2.5 无外键约束
**全库零 FOREIGN KEY**。表与表关联仅通过应用层 ORM 维护，便于分库分表、读写分离。

## 三、跨端共享层（5 张表）

### 3.1 `tenant` — 租户主表

平台所有租户的统一入口。

| 字段 | 类型 | 说明 |

| `name` | varchar(32) | 租户名称（全局唯一） |

**关键索引**：
- `tenant_name_unique` (name)
- `idx_type_status` (tenant_type, status)
- `idx_parent_type` (parent_tenant_id, tenant_type)

### 3.2 `rules` — Casbin 权限规则表

单表存所有三端权限规则，靠 `v1` (dom) 隔离。

| 字段 | 含义 |
|---|---|
| `ptype` | `p` (策略) 或 `g` (角色映射) |
| `v0` | sub: 主体, 格式 `pmc:{uid}` / `tmc:{tid}:{uid}` / `mmc:{tid}:{uid}` |
| `v1` | dom: 域, 格式 `pmc` / `tmc:{tid}` / `mmc:{tid}` |
| `v2` | obj: 资源（permission_key, e.g. `order:export`） |
| `v3` | act: 操作（GET/POST/...）|
| `v4`/`v5` | 保留 |

**关键索引**: `idx_ptype_v0_v1`, `idx_v1_v2`

### 3.3 `data_permission_policy` — 数据权限策略

跨三端共享数据权限规则，单表通过 `platform + tenant_id` 隔离。

| 字段 | 说明 |
|---|---|
| `platform` | DEFAULT 'pmc'，可选 pmc/tmc/mmc |
| `tenant_id` | PMC端=0 |
| `user_id` / `position_id` / `role_id` | 三选一（主体维度） |
| `policy_type` | SELF/DEPT_SELF/DEPT_TREE/ALL/CUSTOM_DEPT/CUSTOM_FUNC |
| `resource` | 作用资源 (e.g. order/customer/finance) |
| `value` | json 自定义策略值 |

### 3.4 `attachment` — 通用附件

平台所有上传文件的统一索引（订单合同、行程单、发票、头像等）。

### 3.5 `migrations` — 框架自带

Hyperf 框架的数据库迁移版本表，0 业务字段。

## 八、关键设计权衡说明

### 8.1 为什么 user 表物理拆三份而非单表 + user_type 字段？

| 单表 + user_type | 三端拆三表 |
|---|---|
| 表大锁竞争 | 锁隔离 |
| 字段长尾（is_owner/employee_no 只 TMC/MMC 用） | 字段精简 |
| 唯一约束复杂（要 case by case） | 唯一约束直观 |
| 拖库一锅端 | 隔离 |
| 升级影响三端 | 独立迭代 |

### 8.2 为什么三方授权反而单表共享？

三端数据结构完全一致 + 业务上需要支持"同一微信账号同时绑 PMC 工号 + 商户工号"，单表 + platform 字段最优。

### 8.3 为什么所有 `*_menu` 表都没有 tenant_id？

菜单是**平台统一定义、套餐分发**的，单个租户不能自定义新菜单（防止前端代码爆炸）。租户的菜单可见性通过套餐 `*_package_menu` 控制。

### 8.4 为什么没有外键约束？

- 便于分库分表 / 读写分离
- 避免 DDL 阻塞
- Hyperf ORM 在应用层做关联约束

### 8.5 为什么 phone/email 要三个字段？

| 单字段加密 | 三字段法 |
|---|---|
| 列表必须解密 N 行 → 慢 | 列表用脱敏明文，0 解密 |
| 精确查找必须全表 decrypt + WHERE → 灾难 | hash 字段索引秒查 |
| 唯一约束做不了 | hash 字段唯一索引 |

性能对比：单字段全表解密 vs hash 索引秒查 **相差 100 倍以上**。
