## 一、项目概览

### 1.1 项目基本信息

| 维度 | 内容 |
|------|------|
| 项目名称 | 温州华夏航服管理系统 |
| 项目定位 | B2B2C 航空旅游综合服务平台 |
| 核心业务 | 机票、火车票、酒店预订 + 积分商城 + 扩展业务(用车/门票/旅行高定) |
| 系统组成 | 7端: PMC平台端、TMC集团端、MMC商户端、Web客户端、小程序客户端、开放平台、App端(扩展) |
| 技术栈 | 后端: Hyperf 3.1 + Swoole / 前端: Vue 3 + Vite + TypeScript / 小程序: uni-app |
| 权限体系 | 三端共用 Casbin 权限验证逻辑，各自独立权限表 |
| 开发周期 | 14-18个月，分4期交付 |

### 1.2 三端定位与层级关系

```
┌─────────────────────────────────────────────────────────┐
│  PMC - Platform Management Center (SaaS平台管理端)        │
│  表前缀: pmc_*                                           │
│  职责: 全局管理、技术对接上游采购渠道、授权TMC、开放平台管控  │
├─────────────────────────────────────────────────────────┤
│  └── TMC - Team Management Center (集团管理端)            │
│      表前缀: tmc_*                                       │
│      职责: 管理旗下MMC、配置采购渠道与结算方式、外采管理      │
│      ├── MMC-子公司 (内部OA模式)                          │
│      │   表前缀: mmc_*                                   │
│      │   特征: 员工验权绑定部门角色，自费在线支付/公费审批抵扣 │
│      │                                                   │
│      └── MMC-分销商 (外部销售模式)                        │
│          表前缀: mmc_*                                   │
│          特征: 传统销售模式，C端用户在线支付                 │
└─────────────────────────────────────────────────────────┘
```

**关键业务规则:**
- MMC与子公司同级，TMC可自定义MMC的title、权限、分润模式、结算方式
- MMC可独立与航司签约大客户协议，但同一员工在同一家航司只能隶属一个签约公司
- TMC如需拥有自己的小程序，只需创建一个同名的MMC即可

### 1.3 Corporate(航司大客户)体系

```
Corporate (航司大客户 corporate_*)
├── 与航司签约的集团/组织，享有不同的政策折扣和服务
├── 与MMC无直接关联，独立管理体系
├── 出票时自动匹配大客户政策 + 前置指令
├── TMC或MMC都可独立与航司签约大客户协议
└── 员工在同一家航司大客户名单中只能隶属一个签约公司
```

## 二、业务架构分析

### 2.1 核心业务流程全景

```
                        ┌──────────────────────────────────┐
                        │          C端用户(小程序/Web)       │
                        │    搜索→比价→下单→支付→出票→出行    │
                        └──────────┬───────────────────────┘
                                   │ 必须归属于某个MMC商户
                                   ▼
                        ┌──────────────────────────────────┐
                        │          MMC商户端                │
                        │  接收订单→(自动/手动)采购→出票     │
                        │  结算: 预付/月结/信用额度          │
                        └──────────┬───────────────────────┘
                                   │
                                   ▼
                        ┌──────────────────────────────────┐
                        │          TMC集团端                │
                        │  管理MMC→配置采购渠道→配置结算      │
                        │  可外采(直连航司)或内采(走PMC)      │
                        └──────────┬───────────────────────┘
                                   │
                          ┌────────┴────────┐
                          │                 │
                     内采路径            外采路径
                          │                 │
                          ▼                 ▼
                   ┌──────────┐      ┌──────────────┐
                   │ PMC平台端 │      │ 外部采购渠道   │
                   │ 统一技术   │      │ TMC自行签约   │
                   │ 对接上游   │      │ 导出→导入核销  │
                   └──────────┘      └──────────────┘
```

### 2.2 订单流转完整链路

**路径1: 内采链路 (MMC→TMC→PMC→采购)**
```
C端下单 → MMC接单 → 订单传至TMC → TMC转发PMC → PMC对接上游采购渠道出票
结算: C→MMC(实时支付) → MMC→TMC(预付/月结/信用额度) → TMC→PMC(预付/月结)
```

**路径2: 外采链路 (MMC→TMC→外采)**
```
C端下单 → MMC接单 → 订单传至TMC → TMC通过自签采购渠道直采
结算: C→MMC(实时支付) → MMC→TMC(预付/月结/信用额度) → TMC→供应商(直付)
```

**路径3: 外采核销链路**
```
TMC选择订单 → 导出Excel模板 → 人工在航司B2B出票 → 填入票号/PNR → 导入系统核销
注意: MMC无外采权限，不具备导入核销功能
```

### 2.3 采购与出票规则

**自动采购规则（三层各自配置，颗粒度越细越好）:**

| 配置方 | 配置维度 | 说明 |
|--------|---------|------|
| PMC | 按采购渠道、航司、产品类型 | 平台级默认规则 |
| TMC | 按航司、航线、金额、时间、渠道 | 可覆盖PMC默认规则，配置外采渠道 |
| MMC | 按航司、航线、金额、时间 | 选择TMC提供的采购渠道列表，配置自动采购规则 |

**出票降级策略:**
- 航司价格实时波动，C端查询价格存在缓存误差
- 自动出票配置阈值和比对规则，验价时满足条件即可出票
- 机票订单异步响应: 用户支付后排队等待购票
- 实在无票时: 人工介入联系客户改签或退票

### 2.4 结算体系

```
┌─────────────────────────────────────────────────────────┐
│                    三层结算体系                            │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  C端用户 → MMC商户: 实时支付(微信/支付宝)                  │
│  MMC商户 → TMC集团: 预付/月结/信用额度(TMC配置)            │
│  TMC集团 → PMC平台: 预付/月结/信用额度(内采路径)            │
│  TMC集团 → 供应商:  预付/月结/信用额度(外采路径)            │
│                                                         │
│  关键规则:                                               │
│  - MMC在TMC中的支付额度由TMC授权配置(信用/预付)             │
│  - 额度不足时C端用户不能下单，下单时实时校验额度             │
│  - 内采: TMC支付给PMC                                    │
│  - 外采: TMC直接付给供应商                                │
└─────────────────────────────────────────────────────────┘
```

### 2.5 利润与分润模型

**利润模式:**
```
销售价 = 上游采购价 + 固定加价 + 浮动比例加价 (+ 可能的服务费)
```

**分润模式 (两层后返奖励):**
| 层级 | 方向 | 说明 |
|------|------|------|
| PMC → TMC | PMC从TMC的采购额中分润 | 平台服务费 |
| TMC → MMC | TMC从MMC的销售额中分润 | 后返奖励 |

**分润配置:**
- 分润计算方式: 由上游配置(固定/比例/阶梯)
- 分润时机: 按订单 / 按周期结算
- 可配置化

### 2.6 审批流程体系

**三种审批实现模式:**

| 模式 | 场景 | 流程 |
|------|------|------|
| 模式1: 先审后单 | MMC内部OA | 用户在MMC端创建审批单(含航线行程+员工信息) → 审批通过 → MMC端直接下单 |
| 模式2: 审批下单 | C端差旅 | C端用户支付时选择"差旅审批" → MMC端审批通过 → 自动下单 |
| 模式3: 先付后审 | C端报销 | C端用户在线支付下单 → 在配置期限内(如7日)提交差旅审批 → 审批通过 → 原路退回 |

**审批流程设计器能力:**
- 可视化拖拽式流程设计器
- 支持条件分支(如: 金额<500免审, 500-2000部门主管, >2000总经理)
- 支持会签(全部通过)、或签(任一通过)、依次审批
- 审批节点支持: 同意、拒绝、办理完成、转交、撤销、终止
- 审批人选择: 角色、发起人本人、上级、指定成员、连续多级上级、发起人自选
- 审批为空时: 转交审批管理员/指定人员
- 独立审批流程，开启OA审批差旅功能时需绑定已创建的审批流程

## 四、技术架构预留

### 4.1 微服务拆分预留

| 预留项 | 具体做法 |
|--------|---------|
| 全链路trace_id | 所有日志表增加 trace_id + span_id，HTTP入口生成，MQ消息传递 |
| 领域事件抽象 | 核心业务变更发出领域事件(如OrderPaidEvent)，当前单体同步调用，后续可切异步 |
| 数据库按领域预拆分 | 表前缀和命名严格按领域组织(order_/finance_/member_/air_等) |
| 接口层领域隔离 | Controller严格按领域划分，避免跨领域直接调用Model |
| 配置外部化 | 所有业务规则配置存数据库(rules表扩展)，不硬编码 |

### 4.2 异步队列设计

**必须异步处理的场景:**
- 出票请求（航司接口响应慢）
- 退款审核通过后的打款
- 大客户白名单批量导入
- 月结账单生成
- 积分过期处理（定时任务）
- 航变通知推送
- 订单状态变更后的事件通知（消息/短信）
- 采购核销（外部导入匹配）

**队列任务版本控制:**
- 每个任务实例带版本号
- 失败重试时可追溯到产生该任务时的业务数据快照
- 保证代码升级后旧版本任务仍可正确执行

### 4.3 扩展业务集成预留

| 扩展业务 | 集成策略 |
|---------|---------|
| 用车服务 | order_item_car扩展字段 + 对接滴滴/高德API预留 |
| 景区门票 | 通用订单项接口 + 基础数据表预留 |
| 旅行高定 | 通用订单项接口 + 行程模板扩展点 |
| App端 | uni-app多端编译，共享C端逻辑 |

**设计原则:** 高内聚低耦合，确保扩展业务可平滑接入当前订单系统

## 五、风险与建议

### 5.1 技术风险

| 风险项 | 影响 | 建议措施 |
|--------|------|---------|
| 航司接口稳定性 | 出票失败影响用户体验 | 异步队列+自动重试+人工兜底+价格阈值验价 |
| 价格缓存误差 | C端展示价与实际价不一致 | 验价阈值配置+差异提示+锁定机制 |
| 多端权限复杂度 | 三端权限体系维护成本高 | 统一Casbin逻辑+权限配置模板化 |
| 数据库扩展性 | 单体架构后续拆分困难 | 严格领域划分+trace_id全链路+领域事件抽象 |

### 5.2 业务风险

| 风险项 | 影响 | 建议措施 |
|--------|------|---------|
| 信用额度风险 | MMC超额消费导致TMC坏账 | 下单时实时校验额度+超额预警+自动冻结 |
| 外采核销时效 | 导入核销延迟导致账务不一致 | 核销超时预警+定期对账任务 |
| 大客户政策冲突 | 员工多重归属导致政策歧义 | 严格唯一性校验+政策优先级配置 |
| 小程序审核 | MMC独立小程序需单独审核 | 提供标准模板+可配置化装修减少审核风险 |
