## 二、问题与建议

### 2.1 WARNING — 设计一致性问题 (需确认)

#### W1. 审批模块方案冲突 (最高优先级)

**现状**: V11同时包含两套审批表:
- **方案A**: 自建审批流程设计器 (approval_flow/node/edge/condition_group/condition_item/form) — 6张表
- **方案B**: 对接第三方OA (oa_config/user_mapping/callback_log) — 3张表
- **共享**: approval_instance + approval_record 同时包含两套字段

**问题**: 
1. 已确定对接第三方OA为主方案，但流程设计器6张表仍保留
2. approval_instance有29列，同时包含 `oa_platform`/`oa_process_id` (OA字段) 和 `flow_id`/`flow_version` (设计器字段)，逻辑混乱
3. approval_node/edge/condition_* 表缺少 tenant_id

**建议**: 
- **如果确认OA为主方案**: 删除approval_flow/node/edge/condition_group/condition_item/form 6张表，approval_instance移除flow_id/flow_version等设计器字段，仅保留OA同步字段
- **如果两种方案共存**: approval_instance应拆分为两套，或通过 `source` 字段区分(自建流程/OA对接)

---

#### W2. 业务表缺少 tenant_id (多租户隔离)

以下24张业务表缺少 `tenant_id`，在多租户场景下可能导致数据泄露或查询性能问题:

| 分类 | 表名 | 影响分析 | 建议 |
|------|------|---------|------|
| **审批流程** | approval_node | 审批节点属租户私有 | 加 tenant_id |
| | approval_edge | 同上 | 加 tenant_id |
| | approval_condition_group | 同上 | 加 tenant_id |
| | approval_condition_item | 同上 | 加 tenant_id |
| | approval_form | 同上 | 加 tenant_id |
| | approval_record | 审批记录需租户隔离 | 加 tenant_id |
| **售后子表** | after_sale_flight | 主表有但子表独立查询需过滤 | 冗余 tenant_id |
| | after_sale_hotel | 同上 | 冗余 tenant_id |
| | after_sale_train | 同上 | 冗余 tenant_id |
| **收藏子表** | favorite_flight | C端收藏查询需租户隔离 | 冗余 tenant_id |
| | favorite_hotel | 同上 | 冗余 tenant_id |
| | favorite_mall | 同上 | 冗余 tenant_id |
| **通知** | notify_config | 通知配置按租户不同 | 加 tenant_id |
| | notify_inbox | 站内信需租户隔离 | 加 tenant_id |
| | notify_template | 模板按租户定制 | 加 tenant_id |
| **开放平台** | open_api | API属于TMC租户 | 加 tenant_id |
| **采购** | procurement_channel | 采购渠道若按TMC配置需隔离 | 确认:PMC全局则不需,TMC配置则需 |
| | procurement_verify_log | 核销日志需租户隔离 | 冗余 tenant_id |
| **队列** | queue_task | 任务数据含租户敏感信息 | 加 tenant_id |
| **供应商** | supplier | 供应商可能租户私有 | 确认:全局共享还是租户私有 |
| **优惠券** | coupon_user | 用户领券需租户隔离 | 冗余 tenant_id |
| **评论** | comment_image | 图片需跟随主表租户 | 冗余 tenant_id |
| **广告** | ad_slot | 广告位按租户管理 | 确认:全局还是租户私有 |
| **标签** | user_tag_relation | 标签关联需租户隔离 | 冗余 tenant_id |

> **子表冗余 tenant_id 的理由**: 虽然可以通过JOIN主表获取tenant_id，但高频查询场景下:
> 1. 子表独立查询(如按航线查收藏)需JOIN主表才能过滤租户，性能差
> 2. 数据权限中间件(Casbin)通常要求每个查询表都有tenant_id才能自动注入条件
> 3. 微服务拆分后子表可能独立服务，JOIN主表不可用

#### S2. order_tag 字段类型建议

**现状**: `order_tag varchar(64)` — 单标签
**建议**: 改为 `order_tag json` — 支持多维度标签

```sql
-- 当前: 单标签, 只能存一个值
order_tag varchar(64) COMMENT '订单标签'

-- 建议: JSON多标签, 支持多维度
order_tag json COMMENT '订单标签(JSON: {"source":"open_api","tmc_id":1,"mmc_id":2,"promotion":"summer_2026"})'
```

**理由**: 
- OpenAPI订单需要标识来源TMC和MMC
- 促销活动订单需要标识活动
- 大客户订单需要标识企业
- 后续扩展灵活，无需加列

#### S3. 评论表设计建议

**现状**: `comment_order` + `comment_image` (仅支持订单评论)，原有 `mall_comment`/`mall_comment_image` (仅商城评论)

**建议**: 保持分表策略(已确认不同业务不同评论表)，但 `comment_image` 应拆分为各业务独立图片表:
- `comment_order_image` — 订单评论图片
- 商城评论图片继续用 `mall_comment_image`

**理由**: 避免comment_image成为各业务评论的交叉表，保持数据隔离

#### S4. order_item_car 用车服务字段扩展

**现状**: 新增了 `car_no`, `fee_detail`, `service_type` 三个字段
**缺少**: `pickup_address`, `dropoff_address`, `pickup_time`, `car_model`, `driver_info`

**建议**: 补充完整用车字段或使用JSON扩展字段:

```sql
ALTER TABLE `order_item_car` 
  ADD COLUMN `pickup_address` varchar(256) NULL COMMENT '上车地址' AFTER `service_type`,
  ADD COLUMN `dropoff_address` varchar(256) NULL COMMENT '下车地址' AFTER `pickup_address`,
  ADD COLUMN `pickup_time` datetime NULL COMMENT '预约用车时间' AFTER `dropoff_address`,
  ADD COLUMN `car_model` varchar(64) NULL COMMENT '车型' AFTER `pickup_time`,
  ADD COLUMN `driver_info` json NULL COMMENT '司机信息(JSON: name/phone/plate)' AFTER `car_model`;
```

#### S5. tmc_package_change_log 增加 trace_id

```sql
ALTER TABLE `tmc_package_change_log` ADD COLUMN `trace_id` varchar(64) NULL COMMENT '全链路追踪ID' AFTER `change_content`;
```

## 四、复核结论

| 评级 | 说明 |
